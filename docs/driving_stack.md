## Current Architecture

The repository currently has three overlapping drive paths:

1. `cmr_controller_remote/connect.py` converts UDP controller packets into ROS topics.
2. `cmr_rovernet/drivesnet.py` consumes those ROS topics and talks to real Moteus hardware.
3. `cmr_controls/swerve_controller_node.py` and `cmr_controls/gazebo_drive_bridge.py` provide separate autonomy/simulation-oriented drive paths.

Those paths are related, but they are not fully unified. In practice, the repo mixes legacy rover hardware control, autonomy topics, and newer Gazebo bridge code.

### 1. Remote Controller Ingress
Source: `src/cmr_controller_remote/cmr_controller_remote/connect.py`

`connect.py` listens on UDP and republishes the decoded controller state into ROS:

- Drive UDP port: `5010`
- Arm UDP port: `5020`
- Mini-arm UDP port: `5030`

Publishers:
- `/arm_controller/cmd_buttons`
- `/arm_controller/cmd_vel`
- `/drives_controller/cmd_buttons`
- `/drives_controller/cmd_vel`
- `/mini_arm_controller/cmd_pos`

Subscriptions:
- None found

Implementation notes:
- The first four UDP bytes are scaled from `0..255` into `-2.5..2.5`.
- Drive axes are packed into a `TwistStamped` in a nonstandard layout:
- `linear.x = lx`
- `linear.y = ly`
- `angular.x = rx`
- `angular.y = ry`
- Button bytes `4..11` become `ControllerReading.button_array`.

## Important Mismatches To Keep In Mind

- `connect.py` publishes joystick data in a nonstandard `TwistStamped` field layout. Any downstream consumer has to know that convention.
- `drivesnet.py` and `swerve_controller_node.py` overlap conceptually, but they are not one shared implementation.
- The hardware autonomy topic name in `drivesnet.py` is `/autonomy_move`, while the newer autonomy/sim code uses `/autonomy/move/...` topics.
- The simulation bridge is newer and cleaner than the legacy rover hardware path, but it is still an adapter rather than the canonical drive controller.
